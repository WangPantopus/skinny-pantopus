# Home invitation sender command contract

Contract for browser/iOS/Android. Backend acceptance is recorded in the
[sender recovery report](home-invitation-sender-recovery-2026-09-12.md); each client
retains its own installed/browser acceptance requirements.
Every endpoint is authenticated, `Cache-Control: private, no-store`.
Except session, all require `x-pantopus-session-scope` from a fresh session read.

- `GET /api/homes/invitations/sender/session` returns `{session:{actor_id,session_scope}}`.
- `GET /api/homes/:homeId/invitations` returns `{invitations,session}` for a current manager, including expired pending invitations and pending invitations from former managers. Status remains `pending`; `expires_at` determines expiry. These rows remain available for explicit withdrawal even when resend is unavailable.
- `POST /api/homes/invitations/sender/context` takes `{home_id,action,payload}` for create, or `{home_id,action,invitation_id}` for resend/withdraw. Returns `{home_id,action,decision_token,invitation,session}`. `invitation` is null for create; otherwise current safe sender invitation details (no token/hash). This is a current authority/terms read, never submission. List and context invitation include `invitee:{id,username,name}|null`: id matches invitee_user_id, username/name are string or null. The displayed profile is locked and included in the context hash. Label targeted account invitations with that current safe identity; never invent a name. Receipt history does not contain this profile.
- `POST /api/homes/invitations/sender/commands` takes `{request_id,token,...intent}`. Intent is exactly the context input plus `decision_token`. `token` is client-generated cryptographically random 32 bytes encoded lowercase 64 hex for create/resend, null for withdraw. Prepare first, then retain this entire original in account-bound protected storage before submission. Create payload supports current `email,user_id,username,relationship,preset_key,start_at,end_at,message` string/null fields. Prefer stable user_id for selected users. UTC dates retain current behavior.
- `GET /api/homes/invitations/sender/commands/:requestId` reads saved history for the current actor.
- `POST /api/homes/invitations/sender/commands/:requestId/cancel` takes the exact original `{token,...intent}`. Cancellation tombstones an unseen original. An already committed result wins. Cancellation of an attempt is distinct from withdrawal of an invitation.

A historical receipt is `{state,home_id,invitation_id,action,decision_token,command:{actor_id,request_id,created_at,updated_at},delivery:{email,in_app},session,message}`. `state` is completed/rejected/cancelled (pending reserved for unresolved transport compatibility). `invitation_id` is nullable for unsuccessful create. Never recover invitation tokens, recipient contact/message, policy or addresses from history. Use the protected original token to share a successful creation/resend link. History grants no current management authority or membership.

Delivery values: email = `not_requested|unconfirmed|provider_accepted`; in_app = `not_requested|unconfirmed|saved`. `provider_accepted` proves only email transport acceptance, not inbox delivery; `saved` proves an in-app notification row, not push/device delivery. A completed command with unconfirmed delivery is still saved. Reads/retries never send again; explicit resend is a new reviewed command and adds a new hash-only capability alias without invalidating earlier links or prepared recipient decisions. No automatic renewal of expiry/access dates.

List/context retain both recorded role fields. Display `proposed_role_base` when present, falling back to `proposed_role`; this is the role order used by recipient admission. Resend derives that same current policy. Legacy null admission snapshots remain supported only where recipient admission already permits them; invalid current policies and changed non-null snapshots remain rejected. An `access_request:<UUID>` preset is normalized only after its genuine approved request matches the Home, recipient, original resolver and effective role. Older rows without `source_request_id` can identify that matching source through the valid UUID suffix. Missing, malformed or conflicting sources fail with `INVITE_SOURCE_CHANGED`. These checks never rewrite the invitation or its prepared recipient terms. The one-shot delivery claim checks current resend eligibility again; lost source or policy leaves the saved command with unconfirmed delivery and no dispatch.

Completed first submission returns 201; read/replay/cancelled returns 200; pending returns 202. Rejected receipts use their 400/403/404/409/410/422 status and add `code,error` while retaining all receipt fields. A missing original returns 404 `INVITE_SENDER_NOT_FOUND` without state (unknown, retain original and offer retry/cancel). Different original under the same request UUID returns 409 `INVITE_SENDER_CONFLICT` without state. Changed prepared terms returns a retained rejected receipt 409 `INVITE_SENDER_CHANGED`. Scope mismatch returns 409 `SESSION_SCOPE_CHANGED`; malformed/unavailable reads return safe 503 and must retain original. Other nonreceipt failures never prove a command did not commit.

For withdrawal, current members.manage is required even for the original inviter. Only pending invitations may be withdrawn; accepted/revoked/resolved status rejects a new withdrawal. No command deletes or changes membership. Losing current authority does not erase historical receipts. Acknowledgement retires local protected originals; do not resubmit terminal receipts. Logout/account changes retire callbacks and dispatch scope; recover only under the original actor using a newly fetched session scope.
