# Android emulator audit — October 17, 2026

This records six rounds of Android walkthroughs and repairs, not a certification that every feature or device works. The founder requested the latest master, a real Android emulator walkthrough, immediate repairs where practical, and one PR. No iOS, web, backend, migration, hosted configuration, or launch-scope changes are included.

## Baseline and environment

- Fetched master and started from `5c64fe823f113bf89e7a855486c2e9f2aeef2b43`; checked the live PR list and master CI rather than relying on a handoff's recorded Git state.
- Pixel 6 emulator, Android 15 / API 35, Google APIs ARM64, running on the Mac. Installed the debug APK and used the actual UI, Android document picker, PDF viewer, share chooser, notification settings, and relaunches.
- Dedicated local Node backend and Supabase database, with all 185 canonical migrations applied. Private uploads used a local Supabase S3 bucket. Test accounts, homes, messages, files, and activity were synthetic.
- Used separate owner, household member, and newcomer accounts. Some address/verification/profile fixtures were seeded through the local API/database because credentialed address providers were unavailable. UI creation was used for tasks, maintenance, documents, emergency information, posts, comments, pickup rules, radon answers, and a Plan.
- Kept launch-cut features off. The local database's separate `plans` runtime flag was enabled for the Plans checks; `pulse_redesign` and playdates remained off. The four-tab launch navigation and the optional fifth Plans tab were both exercised.
- No real recipients, charges, hosted data, credentials, device tokens, raw logs, or screenshots are included in this report or PR.

## Remaining findings and dependencies

These are deliberately not marked fixed by this Android PR.

- **Fresh-database manager permissions:** changing the synthetic member to manager left the API's effective permissions at `home.view`, so household tools disappeared. Android followed the returned policy. Read-only document/maintenance checks used explicit local per-person grants. The separately requested backend chat repaired the narrow manager task defaults in unmerged PR 2430; no production role was broadened here. The sixth round used the separate combined local backend to verify that the manager sees Tasks, can create and complete a task, and retains its Done state after relaunch.
- **Public verification badge scope:** the household-only synthetic member appeared as Verified neighbor on their public profile. The profile API returned `residency.verified: true`; `getPublicResidencySummary` checks verified occupancy without distinguishing household verification from address verification. PR 2425 contains the separate identity-projection repair; it is not applied to this Android runtime. This check did not demonstrate a bypass of the separate neighbor-message server gate.
- **Neighbor block after reload:** a confirmed block was enforced by the server, but the current received-note response does not include the persisted blocked state and the screen initializes it to false. PR 2425 contains related backend response changes; Android follow-through and another relaunch check are needed after that lands.
- **Canceled-plan server enforcement:** Android now refreshes the closed-chat state, but the separately requested backend chat found the server write guard was not covered by PR 2425 and repaired it in unmerged PR 2430, including cancellation races and failed room closure. A client-only control is not server authorization.
- **Address-share server admission:** the account-helper reveal route returned HTTP 200 `shared: true` even when neither a home nor inline delivery address existed. Android guards the missing-address state. The sixth pass handed the server finding to the backend session, which repaired both account-helper and email-guest admission in open PR 2436; its CI is green. On the combined local backend, the account helper saw no exact delivery address; the organizer saw “Delivery address unavailable” for both the account helper and email guest, with no Share address or false success claim. No backend source was changed here.
- **Potentially misleading backend content:** system-age estimates derived from home construction year and property-tax date wording need the separate provider/backend repairs in PR 2425. The backend follow-up found that PR 2425 still substitutes building age for missing or explicitly unknown system installation years when the building year is known; that remains open. This PR does not certify those facts.

The backend dependency PRs remain separate from Android PR 2426. The sixth round temporarily connected the installed Android APK to the backend session’s combined real local API/database: manager task creation/completion persisted after relaunch; the canceled plan’s chat retained readable history and no composer; account/guest missing-address rows were honest. A private client-test proxy returned the backend’s `503 AUTH_UNAVAILABLE` contract: the account remained signed in after relaunch, Support Train showed Retry, and recovery restored the train and household tools. This was a native client contract check, not a new database-fault test. No backend changes were cherry-picked or merged here; the usual Android fixture stack remains based on master.
