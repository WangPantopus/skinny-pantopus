# Last review findings for f6-home-basics-rows (round 2). The fix after this round was applied but not re-verified.

- [major] (substance) The status line is only defined for a checklist window that is currently open, yet the prompt asks for frames where the window has not started, has ended, or has no date. In those frames the designer has to guess the line, and either defined string would be false. This breaks the prompt's own honesty rule and its DONE criterion.
  - evidence: Prompt: status text is either "Hidden from your place file · window ends Sat 28 Nov · in 40 days" or "Showing in your place file until Sat 28 Nov · in 40 days", and "the line must never claim something false". DONE WHEN: "The status line always matches whether the checklist is hidden or showing." But artboard 8 (Sun 1 Nov, restore row absent) would get "Showing in your place file until Thu 31 Dec" even though the checklist doesn't show until 1 Nov. Artboard 9 (Fri 14 Aug, restore row present) would get "window ends Tue 13 Oct · in …" for a date already past. Artboard 7 ("Not set") has no date for a status line at all. Inventory states: "future date or >60 days ago (warn the rows will not appear)".
  - fix: Add status-line variants and name each one in artboards 7–9: no date → no status line (the helper alone). Future date → "Starts Sun 1 Nov · in 13 days · runs until Thu 31 Dec", with no 'Showing' wording. Window ended → "Ended Tue 13 Oct · won't show now", whether hidden or not, in place of the hidden/showing text. List these strings in COPY and under the invented strings on Notes.
- [minor] (substance) The prompt says a new home always arrives "Not set" and that this row is the only way to set the date. That is wrong about the product. On the natives, the add-home wizard stamps today's date from a checkbox (Maya's own stamped Sun 18 Oct comes from this), and the web editor at /app/homes/[id]/edit can already change move_in_date.
  - evidence: Prompt: "A new home arrives with Moved in set to 'Not set', because a saved place has no move-in date; until the claim flow asks for the date, this row is the only way to set it." Inventory uxNote: "both natives can only ever stamp move_in_date = today from an add-home checkbox". derive-proposals hostSurface: "linking to the existing editor at /app/homes/[id]/edit/page.tsx:320".
  - fix: Change it to: "A home claimed from a saved place arrives 'Not set'; a home added with the 'just moved' checkbox arrives stamped with the add date. On iOS and Android this row is the only correction path; web also has the Edit home page, which should be linked to or replaced by this row (note it on Notes)."
- [minor] (substance) The derive proposal lists a second way to set the date: an inline 'Just moved in? Tell us when' ask that writes the same field. The prompt doesn't mention it, and the Notes don't say whether that ask survives in the place file.
  - evidence: derive-proposals f6-home-basics-rows entryPoints: "The 'Just moved in? Tell us when' prompt state on the Just Moved card writes the same field inline". The prompt's arrival path (2) covers only the place file's "Not set" row.
  - fix: Add a Notes line saying the inline 'Just moved in? Tell us when' ask is now the place file's Moved in 'Not set' row, which lands here, so there is only one write path.
- [minor] (substance) The entry path is not the one in the sources. The derive proposal names Place dashboard → Home tools → Settings, and a nav-only settings index on iOS. The prompt says Settings is reached from the home header's overflow menu and assumes existing Address and Home name rows on every platform.
  - evidence: derive-proposals: "Place dashboard → Home tools → Settings; web /app/homes/[id]/settings → Edit home; Android homes/{id} settings; iOS per-home settings index", and "HomeSettingsViewModel.swift (today nav-only, one nickname PATCH)". Prompt: "(1) Settings, from the home header's overflow menu" and "under the existing Address and Home name rows".
  - fix: Use "Place → HOME A → Home tools → Settings". Add: "If the iOS screenshot has no Home Info group with Address and Home name rows, add the two rows as the group's first rows and record this on Notes."
- [minor] (substance) The Moved in sheet hides "Not sure of the day" and the ReminderLeadControl, but the DateSheet contract defines neither as a per-kind variant. The Notes list doesn't flag this as a contract gap, although the prompt flags its other gaps.

- [major] (ux) The status line has only two texts, 'hidden' and 'showing', but frames 4, 8 and 9 show states where neither is true. Frame 8 (future date, never hidden) would read 'Showing ... until Thu 31 Dec' although nothing shows until Sun 1 Nov. Frame 9 (window ended, hidden) would read 'window ends ...' for a date that has already passed. Frame 4 (Not set) has no window at all. The prompt's own rule says the line must never claim something false, so this would ship a false status. It also leaves unclear where the future-date and older-than-60-days notes appear, and for how long.
  - evidence: Prompt LAYOUT: "Its text depends on the checklist state for this viewer: while hidden, 'Hidden from your place file · window ends Sat 28 Nov · in 40 days'; while showing, 'Showing in your place file until Sat 28 Nov · in 40 days'." INSTEAD OF: "because the line must never claim something false." ARTBOARDS 8: "Sun 1 Nov 2026 saved with 'starts in 13 days' note"; 9: "Fri 14 Aug 2026 ... restore row present". Inventory states: "future date or >60 days ago (warn the rows will not appear)".
  - fix: In LAYOUT and COPY, replace the two-state status with five states. (1) Showing: 'Showing in your place file · in 40 days · until Sat 28 Nov'. (2) Hidden: 'Hidden from your place file · in 40 days · window ends Sat 28 Nov'. (3) Not started yet: 'Your moving checklist starts in 13 days · Sun 1 Nov' (add ' · hidden from your place file' when hidden). (4) Ended: 'Your moving checklist ran until Tue 13 Oct, so it won't show now' (add ' · hidden' when hidden). (5) Not set: no status line. Make the future-date and older-than-60-days notes these persistent status lines, with the info glyph, instead of separate notes. After a save, prefix 'Saved. ' once, as a polite live region.
