# Last review findings for f3b-verify-address-sheet (round 2). The fix after this round was applied but not re-verified.

- [major] (substance) The TYPE and ATTACH sections are factually wrong about the product. iOS and Android already ship a verify sheet with a 'What this unlocks' list, a method picker and status screens, and the Place dashboard presents it. On web, VerifyPromptSheet already has three hosts. Treating the surface as NEW, and attaching only the native banner, means the designer never sees the existing native sheets this surface replaces.
  - evidence: frontend/apps/ios/Pantopus/Features/Place/Verify/PlaceVerifyFlow.swift: "B1 is a bottom sheet (the \"what this unlocks\" benefits + a method picker)", presented at PlaceDashboardView.swift:88 "PlaceVerifySheet(". Android: PlaceDashboardScreen.kt:119 "PlaceVerifySheet(" and RootTabScreen.kt:2664 "PlaceVerifyStatusScreen(". Web: PlaceDashboardView.tsx:196, NeighborMessageCompose.tsx:211 and PulseStreamView.tsx:186 all render VerifyPromptSheet. The prompt says: "Web has a \"What this unlocks\" prompt but no host that opens it. iOS and Android have only an inline verify banner."
  - fix: Make TYPE an extension or replacement of the existing verify sheets (web VerifyPromptSheet; iOS and Android PlaceVerifySheet plus the status screens). Attach all three current sheets. List what changes: the pre-selected method and the single 'Start verification' button become equal method rows; the '3–7 days' postcard copy becomes '5–10 days'; the benefit tiles become GrantLimitList rows; the caller now sets the reason header. Record each change in Notes.
- [minor] (substance) The design doc says the sheet's 'What this unlocks' list stays unchanged, but the prompt rewrites it into verb rows. Notes do not record this departure.
  - evidence: Design doc F3b: "The verify sheet's 'What this unlocks' list is unchanged and is shown to household members as the next step." The current web BENEFITS list reads "Proof you live here", "Your mailbox and your rank", "What only verified neighbors see".
  - fix: Add to Notes: "The unlock list is rewritten into the shared GrantLimitList verb rows (research: plain verbs), which departs from the doc's 'unchanged'. The current benefit 'Your mailbox ... opens' is dropped because the household mailbox keeps household semantics."
- [minor] (substance) The glyph on the unlock-list rows is never specified. The attestation sheet copies 'the same tick glyph ... as the verify sheet's What this unlocks list', while GrantLimitList draws these same rows with a lock elsewhere, so the two sheets could drift apart.
  - evidence: Attestation prompt: "Grant rows use the same tick glyph, 44pt row height, body type and row order as the verify sheet's \"What this unlocks\" list". The verify prompt names only the "verify sheet unlock list variant: heading, two rows, \"and 3 more\"" and gives no glyph.
  - fix: In LAYOUT, add: "Unlock rows use the 16pt success tick, body text.primary, 44pt rows, in the same order as the attestation grants."
- [minor] (substance) At the medium detent only the first two methods are visible, so in frame 1 the Ask row, the path the flow depends on, sits below the fold. The derive proposal asked for the unlock list and the method list to fit above the fold.
  - evidence: Prompt: "It opens at medium and shows the reason, the unlock list and the first two methods." derive-proposals: "the unlock list and the method list must both fit above the fold on a phone". flows-spec step 13: "'Ask Dana Whitfield to confirm · Usually same day' is offered. He taps it."
  - fix: Either open at the large detent when a method is unavailable, or state in Notes that the medium detent hides methods 3–4 and that a visible cue ('and 2 more ways' or the grabber) is drawn in frame 1.
- [minor] (substance) A DONE WHEN line misstates the layout: it places the reason header under the unlock heading, when LAYOUT puts the header above it.
  - evidence: DONE WHEN: "The header says why the sheet opened, under the \"What this unlocks\" heading." LAYOUT: "order is header (title, Close, reason, address, ScopeChip), then the \"What this unlocks\" heading".
  - fix: Change to "The header says why the sheet opened, above the unchanged 'What this unlocks' list."
- [minor] (substance) The didn't-confirm state does not say whether the Ask row stays or can be used again. Only the unanswered state gets 'Ask Maya again'.
  - evidence: COPY: "Maya didn't confirm: \"Maya didn't confirm. You can still verify by postcard or with a document.\"" Frame 5: "Postcard and Document offered."

- [major] (ux) The iOS medium detent cannot hold the content the prompt assigns to it. The header (title, 2-line reason, 2-line address, ScopeChip) is about 184pt. The unlock heading, 2 rows and 'and 3 more' add about 160pt. Two method rows add at least 64pt plus about 110pt, because the Document requirement alone is about 140 characters and wraps to 3-4 lines. That is about 520pt against a medium detent of about 426pt. The long requirement lines also undo the 'how fast' scan the chips exist for.
  - evidence: PLATFORMS: "It opens at medium and shows the reason, the unlock list and the first two methods." CONTENT: "'Document' · 'About 1 day' · 'Accepted: a lease, rental agreement or utility bill from the last 90 days, with your name and this address. A Clark Public Utilities bill works.'" INTERACTION: "Tapping Document shows the accepted types".
  - fix: Change PLATFORMS to: "iOS opens at the large detent. The medium detent is used only for the single-line states (no method available, access ended)." Shorten each requirement to one line of 60 characters or fewer: Postcard "We mail a code to 2418 NE Larkspur Loop." · Document "A lease or utility bill with your name on it." · Landlord "We email the landlord on the lease." · Ask "Maya claimed this address and can confirm." Move the 90-day rule and the Clark Public Utilities example to the Document choose step (frame 11).
- [major] (ux) One tap on the Ask row sends Maya a push and an in-app row, with no confirm and no Undo, and the request can never be withdrawn. This breaks P19: anything that notifies another person waits until undo closes. It also breaks the flow, because the attestation prompt assumes Sam can withdraw his request. The Postcard row, by contrast, gets an inline confirm.
  - evidence: INTERACTION: "Tapping Ask sends the request, and the row becomes the request-sent state in place." ux-research-brief.md P19: "Anything that notifies the household waits until the undo window closes." f3b-owner-attestation EDGE CASES: "If Sam withdraws his request or leaves while the sheet is open".
  - fix: In INTERACTION write: "Tapping Ask turns the row into the request-sent block with an InlineUndo ('Request ready · Undo'). Maya is notified only when Sam closes the sheet. After that, the request-sent block offers 'Cancel request', which is undoable in place and tells Maya nothing." Add 'Cancel request' and 'Request ready · Undo' to COPY and Notes. Add the artboard "ios · NN-request-cancelled · light".
