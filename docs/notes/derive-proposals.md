# F7 — Home-screen widgets (iOS WidgetKit, Android RemoteViews): "Recycling Tue · AQI 42 · Lease notice in 12 days" on the home screen with no notification and no API call from the extension.

**Rationale:** Six surfaces, none on web. F7 is native-only by design and I did not invent a web entry: the web app has no home screen to put a widget on, and the one web-adjacent hole (no ?src= parsing and no session_open call site anywhere in frontend/apps/web/src) belongs to §5/F8's attribution work, not to F7. Worth saying plainly so the parent agent does not expect a web row.

Why more than the doc's two widgets. The doc names exactly two deliverables (a small and medium widget per platform) and then quietly assumes four more surfaces exist. Rule 4 says a surface with no entry point is a bug, and as written the widget has no entry point at all: nothing in either app mentions it, so the only discovery path is a user spontaneously browsing the OS widget gallery. That forces two of my entries (the nudge row and the how-to sheet) and makes a third — the gallery entry itself — a real designed artifact rather than two strings. §5 makes this load-bearing rather than nice-to-have: activation counts "a widget snapshot written, reported by the client as an event" as equal to the briefing toggle, so an undiscoverable widget silently costs a third of the activation definition. The nudge is also the only return trigger that survives a user declining push permission, which is why I argue it should outrank the briefing opt-in for that user.

Why small and medium are two entries and not one. They are two different compositions, not one scaled: the medium holds four text rows, the small holds one promoted fact plus a chip. The doc says "small and medium" and never says what small drops, which is exactly the kind of decision that will otherwise be made twice, differently, by iOS and Android. I gave the small an explicit urgency promotion ladder. I did the same to the medium as a uxRisk: three equal-weight lines give tomorrow's recycling the same emphasis as a lease notice twelve days out, so the better design promotes one hero line and demotes the rest.

Why the tap landing is its own entry. It is the feature's only interactive moment and it is currently broken on Android: DeepLinkRouter.kt:494-503 sends "today" to Destination.HubToday, which RootTabScreen.kt:2226-2233 resolves to the hub briefing screen (GET /api/hub/today) — a different payload from the one the widget mirrors (GET /api/homes/:id/intelligence), and one with no empty state, so a T1 saved-place user gets a hard error from tapping their own widget. iOS avoids it only by accident. The same entry carries the second must-fix: both Today view models are idempotent once loaded (iOS PlaceDetailViewModel.load() :34-37, Android TodayTabViewModel.load()), so "Open to refresh" can open a warm app, write no snapshot, and leave the widget grey permanently — the landing has to call refresh(), not load(). And neither native app has any funnel-event client at all, so the emitter §5 depends on is F7 scope, not F8 scope.

What I deliberately folded rather than listed. (a) The Settings → Notifications → Briefings re-entry row is one row, so it lives inside the how-to sheet's entry points rather than as a seventh entry — but it is required, not optional: without it, one dismissal of the nudge makes the sheet permanently unreachable. (b) The placeholder, stale, unverified-pickup and no-place renderings are states of the widget entries, not separate surfaces, even though each is a distinct drawing — they are listed exhaustively per widget so the design pack still gets them. (c) I did not invent a widget configuration screen: StaticConfiguration is right for a 30-mover pilot where each user has one address, and I recorded the multi-home ambiguity as a uxRisk on the medium instead. (d) I did not add a settings toggle, because F7 introduces no persisted preference — the widget's on/off switch is the OS home screen itself.

Effort adds to roughly 6.75 days per platform against the doc's 6, the difference being the discovery surfaces the doc omitted.

# F8 — Compare card, rotating seasonal headline, positioning line (docs/first-person-loop-design-2026-09-16.md:303-352)

**Rationale:** Nine surfaces, and deliberately not more. F8 is the only feature in this design that touches NEITHER Today screen — it lives entirely in the pre-auth /start funnel (StartFunnel.tsx), its OG image route, and the two native T0 previews. Nothing here reads GET /api/hub/today or GET /api/homes/:id/intelligence, so none of the two-Today confusion applies; I said so explicitly rather than inventing a Today entry.

What I folded rather than counted. (a) The expired/tampered-token banner is a state of the compare arrival header, not a screen — it renders the ordinary hero with one quiet row, and the 'from the card in your mailbox' pill at StartFunnel.tsx:102-110 is the existing precedent for that slot; I flagged that the two now compete for the same position. (b) The recipient's could_not_place and unsupported_region paths are states of the reveal, but they are load-bearing: CouldNotPlace (:585-600) currently resets to the hero and would destroy the sender's column, which contradicts the doc's own 'the token's chips are self-contained' promise — that is a defect, not a design choice. (c) A management/list view for sent compare links is genuinely unnecessary: the token is server-signed and nothing is stored, so there is nothing to list, revoke or delete; the only durable artifact is the recipient's link itself. (d) There is no admin screen for the new compare/spread rates — funnelReport.js feeds GET /api/admin/funnel/summary, which has no UI in this repo.

Why the grade chip row is its own entry. It is the only thing in F8 that is drawn four times (hero column, both reveal columns, sheet preview, OG image) and it has never existed as UI — those four chips are assembled only inside the OG route at route.tsx:61-66. Drawing it once at three sizes is the difference between a coherent card and four divergent ones.

Entry-point gaps I am flagging rather than papering over. A recipient who already has the app taps a /start?vs= link and lands in the mobile browser: iOS DeepLinkRouter (:493-500) reads only deliveryId/kind and Android's router has no vs branch, so there is no native landing target for the single most viral link in the product. v1 accepts that, but then the web compare pages must carry the app-download link. Separately, neither native app has any funnel-event emitter at all, so t0_compare_viewed / t0_share_clicked(method=compare) / session_open from native are unrecorded — the spread metric in §5 is web-only by construction, which understates k rather than inflating it.

Where I pushed back on the doc. Two places. First, 'render the compare header above the hero' and 'show both columns side by side' are written as two literal two-column layouts; at 375px that is eight grade chips plus eight source captions and the address field pushed below the fold. The better surface is a comparison table — one row per layer, sender left, you right — with true columns reserved for >=768px, and a collapsed sender strip above the address field on phones. Second, the doc puts the compare card's privacy sentence in its own §Privacy section; on the sheet it has to sit above the button, with a live preview of the card, or consent arrives after the link already exists.

Effort is per platform per the schema: web totals ~5.5 days across entries 1,2,3,5,7,8,9 against the doc's 'web 3-4 d + OG 1 d' — the gap is the two-column scaffold and skeleton the preview step does not have (it is a fixed max-w-[540px] single column today) and the copy.ts package module that does not exist. Natives are 1 day each as the doc estimates, because they get the seasonal headline free from the server payload and only add two buttons plus a system share sheet.

# F6. Just Moved on the account, plus voter registration (docs/first-person-loop-design-2026-09-16.md:261-276)

**Rationale:** Five surfaces, and only one of them is genuinely new. F6 is described as a migration plus a sixth row, and most of it really is an extension: the Just Moved card exists on all three platforms and only changes its storage, its step count and its states, so that is one entry with three platforms rather than three entries.

What I added beyond the doc, and why. (1) The voter step sheet. The doc routes the step to /app/place/civic, but I verified that Civic detail renders districts, a ballot preview and 'No upcoming election' and has no registration content, and that PlaceSectionDetail requires a claimed primary home — so the doc's own step copy (deadline, three method dates, state office, self-report, 'never claim to know whether the user is registered') has nowhere to live. A sheet keeps the fact next to the tap and is where the honesty labeling and the 'I did this' receipt belong. (2) The Civic registration block, because the card hides 60 days after move-in while the November 3 deadline does not — without it the feature deletes itself before it matters. (3) The move-in date row, because it is the gate for everything: web can edit it (/app/homes/[id]/edit:320) but both natives can only stamp today from an add-home checkbox and have no correction path, so on iOS and Android the acceptance criteria are literally unreachable today. (4) The calendar/Today rendering entry, because seeded state-scoped election_deadline rows will surface through composeForHome into the address-calendar card and, inside the lead window, as an address_calendar signal on the hub Today — whether or not anyone designs for it. F6 does not mention this and it is the most likely place for the 'read as a claim about this address' failure.

What I deliberately folded rather than counted. The dismiss confirmation and undo are states of the card, not a screen; the restore control is a second row on the settings screen I was already extending, so those two share one entry. The 'all six done' celebration, the offline queued-tick chip and the self-report receipt are card states. The 'Just moved in? Tell us when' prompt is a state of the card's currently-empty slot, not a new surface, though it writes the same field as the settings row.

What I did not invent. No push, so no new notification landing target: F6 proposes no reminder, and the generic reminder channel would need an explicit lead_days decision before a deep-link target is worth drawing. No T1 saved-place variant of the checklist: HomeOccupancy is per-user-per-home, so the checklist cannot exist for a saved place at all — that is F2's job, and the two lists must not read as the same thing. No admin surface for seed verification; the state-deadline checking is internal work.

One structural gap to flag rather than design around: every surface here is home-gated, so the mover F1 is designed to win — someone who saved a place and has not claimed a home — sees none of it. And the three Today references are deliberate: the card and the sheet live on the Place dashboard (neither Today), the calendar row lands on Today screen 2 (intelligence), and the same row leaks to Today screen 1 (hub) as a signal.

Effort excludes backend: the doc's migration + route is 1 day and the seed verification 1-2 days, on top of the per-platform days above. The sheet's read path (a rule further out than composeForHome's 14 days) is an unlisted backend line item.

# F5 Important dates (lease end, lease notice, insurance renewal, warranty end, HOA dues, tax appeal, plus pickup day) at T1 (saved place, scope `saved_place`) and T3 (claimed home, scope `home`) — docs/first-person-loop-design-2026-09-16.md:230-259

**Rationale:** Eight entries, seven of which are extensions or cards inside screens that already exist — F5 genuinely needs no new route on any platform, and I resisted adding one. What I did add against the doc is the Your dates card (f5-your-dates-card), and it is not optional: composeForHome (backend/services/addressCalendarService.js:108-166) expands rules only inside windowDays=14, so under the doc's design as written a user saves a lease end eight months out, gets a toast, and the date is then invisible and undeletable in the product until two weeks before it fires. The doc's chosen host — a 14-day window card — structurally cannot be the management surface for annual dates, so its own acceptance criterion ('sees both on Today') is false for almost every date the feature exists to capture. That card is a NEW_CARD_IN_EXISTING rather than a route because the schema caps the list at one row per kind: at most six dates plus pickup, which is a card, not a screen.

I folded rather than split in four places. The pickup-day picker does not get its own entry — making the existing card scope-aware (home | saved_place) is the same change that unblocks pickup at T1, and the doc's separate 'Pickup schedule' toggle should arguably collapse into the date sheet as a seventh kind. The 'Remind me' lead-days control is part of the sheet, not a settings surface. The confirmation toasts are copy inside the sheet. The permission-denied experience for a household member without calendar.edit is a state on three entries rather than a screen — though it exposes a real hole: neither web TodayDetail nor the native Today view models read the home permission model at all, so the intelligence payload has to carry can_edit or the gate cannot be drawn.

I kept f5-t1-calendar-host separate from the card extension even though it renders the same components, because it is different work on a different screen against a different payload. Today exists twice on every platform: F5's card lives on the PlaceIntelligence Today (web /app/place/today, iOS AddressTodayTabView, Android TodayTabScreen) which requires a claimed primary home, while the T1 user's only reachable Today is the hub-payload Today (web /app/today), which carries no address_calendar section at all — pickup reaches it only as a signals[] entry whose kind is not even in the web type union. f5-reminder-landing and f5-household-calendar-dates are entry-point and honesty obligations rather than new product surface. The household calendar merge exists because the T3 toast promises 'your household calendar' and that calendar does not contain AddressCalendarRule rows; it also picks up a free win, since the fully built web household calendar at /app/homes/[id]/calendar currently has no link from anywhere in the app.

On effort: these sum to roughly 5-6 days per platform against the doc's budget of web 1.5 / iOS 2 / Android 2. The gap is almost entirely the management list, the T1 host and the deep-link landing — the three things the doc's effort line assumes are free because it assumed the card it names is reachable at T1 and can display an annual date. # F10 Mail snap — photograph paper mail, extract payee/amount/due date, put it on the address calendar, remind, mark paid (phase 2, post-pilot)

**Rationale:** Nine surfaces, from a feature the doc describes in one dense paragraph of client work ("wire the existing CTAs to the camera, show extracted fields as editable chips, add a web Mail Day page"). The count comes from following the object the user creates all the way through: a photograph becomes an upload, an extraction, a mail piece, a bill, a calendar row, a reminder, and a file that must be deletable — each of those is somewhere the user has to look.

Only two things here are genuinely new full screens, and only on one platform: the web Mail Day triage page (web has no triage surface at all today — /app/mailbox/settings/mail-day is settings plus a read-only summary, and the only wired Mail Day clients are p3/mailday/summary and /settings). Everywhere else I stayed at sheet, card or extend, because the triage screen, the bills surfaces, the address-calendar card, the mailbox drawers and the notification lists all already exist on three platforms. I kept the per-platform disposition split explicit in the contents of f10-1 rather than inventing two entries, since it is one conceptual screen with a 2-day web cost and a 0.75-day native cost.

Surfaces the doc implies but never names, which I added: the photo viewer (f10-4) — the doc promises private, authenticated, deletable storage and then gives the photograph no place to be seen or removed, which would make it write-only; the privacy/storage card (f10-8) — the same promise needs a bulk exit, not per-bill deletion; the push landing (f10-7) — §2 rule 4 demands every push deep-link to the exact surface, and today Android's router has no /homes/:id/bills branch at all and web has no bill detail route, so the monthly-return loop breaks silently; and the photographed mail piece in the drawers (f10-9), which is where the record actually lives after triage ends.

Folded rather than split: the "Scan today's stack" CTA wiring (a state/entry point of f10-1 and f10-2, not a screen); the T1 no-claimed-home tier gate (a state on f10-1, f10-2, f10-3 and f10-6, routed to F5's manual dates — F10 explicitly requires a claimed home in v1); the AI-unavailable manual path (a state of f10-3, not a second sheet); mark-paid confirmation and undo (states on f10-5 and f10-6, since Mark paid already ships on all three platforms); and the web bill delete 'cancelled'/'canceled' bug, which is a one-line fix inside f10-5 but reproduces a visible lie on the newest path.

Two places I pushed back on the doc. The "editable chips" confirmation is the wrong control for a currency, a date and a payee, and it hides which field the model was unsure about — I propose photo-beside-fields with per-field confidence and keep chips only for the collapsed row summary. And treating the camera as a one-shot picker fights the actual task, which is a stack of mail on one evening — the capture tray should be a batch session with a thumbnail strip, and the snap affordance should be persistent rather than living only in the empty state, where both natives currently put it.

Effort lands near the doc's web 4d / iOS 5d / Android 5d, with web slightly over because the doc's estimate assumes a Mail Day page that does not exist and a Mail Day client that is only half-wired.
