# LENS: Data visualization and information design — what should be a mark instead of a string, what encoding makes two addresses comparable without judging a home, and how provenance (OFFICIAL vs UNVERIFIED) is encoded consistently across calendar, push, widget and share card.

**Verdict:** The screen set is a sound information architecture that treats every payload as prose. Four datasets in this repo already have real structure and every one of them ships as a string: a 14-day dated sequence (composeForHome), a 0–500 scalar with six canonical named bands (PlaceAirQualityData.index), a 12-month own-vs-peer money series with k-anon household counts (homeBillComparisonService — rendered as sentences on Android only, nothing on web/iOS), and a 5-slot/21-day founding window (cellFoundingWindow, collapsed to a boolean before it reaches any UI). The blocker is F8's compare token: it declares `g:{flood:"A",wildfire:"C",air:"B",radon:"D"}` while the actual fields are four incommensurable labels — `flood.risk_level`, `wildfire.hazard_label`, `air_quality.category_label`, `Zone N` (og/place/route.tsx:61-66, and note the helper there is named `grade` but returns a label). Letters manufacture a shared ordinal scale that does not exist, carry no legend, and convert "what's on record about an address" into a report card on a home — which is the exact thing the pilot's honesty bar scores at zero. Fix the encoding and most of the compare-layout problem dissolves: two readings on one instrument, not two scorecards. Second systemic problem: UNVERIFIED is expressed four different ways (a row-level string suffix, a parenthetical in push copy, a "·unconfirmed" glyph in the widget, and nothing at all on the compare card or OG image, whose token has no confidence field). That belongs in the mark — filled/hollow — not in repeated prose. Net screens: +1 (a year-at-a-glance timeline, +1; a large widget size, +1; one merged provenance sheet replacing three separate implementations, −1).

## Findings

- **[blocker]** targets: f8-9-grade-chip-row, f8-5-og-compare-card, f8-1-compare-arrival-header, f8-3-compare-sheet
  - problem: The compare token invents letter grades (A/C/B/D) for four layers whose real values are incommensurable labels from four different authorities: flood.risk_level (FEMA zone), wildfire.hazard_label (USFS class 1-5), air_quality.category_label (EPA AQI band), and 'Zone N' (EPA radon zone 1-3). A letter implies one scale, one direction and one legend, and there are none. It also reframes a public record as a score on someone's house — the precise reading the honesty bar counts at zero. A radar/spider is worse for the same reason plus one more: it normalizes four unlike axes onto one radius and encodes area, so a bigger blob reads as a worse home.
  - recommendation: Drop letters entirely; no radar. Use four small-multiple SCALE STRIPS — one per layer, each drawn on its own source's named bands, stacked as four rows. Encoding: a horizontal track segmented into that authority's bands (flood: minimal / 100-yr / coastal; wildfire: USFS 1-5; air: EPA's 6; radon: zones 3-2-1), a marker positioned in the band, the band's plain-language name printed beside it, and the authority as the row caption ('FEMA flood zone', 'USFS wildfire hazard, quarter-mile', 'AirNow, today', 'County radon zone (EPA)'). The track never spans layers, so nothing sums or averages into a verdict. Fallback when a layer has no data: the track renders greyed with no marker and the words 'Not on record' — never a missing row, or the two compare columns silently differ in length. Add `conf` to the compare token and render an unverified reading as a hollow marker; if the token cannot carry confidence, drop unverified layers from the card rather than shipping them as confident.
  - net screens: 0
- **[blocker]** targets: f8-2-compare-reveal, f8-5-og-compare-card
  - problem: The reveal is specified as two literal side-by-side cards. At 375px that is eight chips plus eight source captions, and the preview step is a fixed max-w-[540px] single column today. Two facing cards also make the comparison implicitly evaluative — two scorecards invite a winner — which is the neighbor-judgment failure mode.
  - recommendation: One shared-scale comparison table: four rows, one per layer, each row a SINGLE track carrying BOTH marks — sender as a filled dot, 'You' as a ringed dot — with the layer name above and the two plain-language band values left and right beneath. This is the mark that makes the comparison read as two readings on one instrument rather than two verdicts, and it works identically at 375px and 1200px, which also solves the OG card. Order rows by distance between the two marks, descending, so the one real difference is row 1 — never a fixed order and never 'worse first'. Design the state the doc omits and that will be the most common outcome: both marks land in the same band, which should render as a merged mark and the words 'Both minimal' rather than two dots a pixel apart. Recipient geocode failure keeps the sender's marks on every track (the doc's own 'self-contained token' promise) instead of CouldNotPlace resetting the funnel. Reserve true two-column cards for >=768px only as a presentation of the same rows.

  - problem: The address calendar is the product's signature dataset — a dated 14-day sequence with kind, confidence, source and lead_days per item — and every surface renders it as a vertical list of text rows. A list cannot answer the one question a two-week window exists to answer ('is anything happening this week, and when'), and it gives the empty state nothing to show but a sentence, so 'nothing on the calendar' is visually indistinguishable from a section that failed.

This gives F4's 'tonight' row a spatial anchor (cell 2 emphasized, not an alert banner), gives F6's statewide election deadline a way to sit in the strip visually marked as not-this-address (a bar spanning the cell's full height rather than a dot), and gives the empty state 14 drawn-but-empty cells, which reads as 'checked, nothing found' instead of 'broken'. - **[major]** targets: f12-calendar-row-provenance, f4-1-pickup-push, f7-today-widget-medium, f8-9-grade-chip-row, f5-your-dates-card
  - problem: UNVERIFIED is encoded four incompatible ways for the same fact: a per-row string suffix ('· unconfirmed, please double-check', AddressCalendarCard.tsx:87), a parenthetical inside push copy, a '·unconfirmed' glyph in the widget, and nothing at all on the compare card or OG image — whose token schema has no confidence field, so a seeded unverified radon zone would unfurl in a chat thread as a confident grade. Words then appear once per surface as a single legend line ('Hollow = on record, not yet confirmed'), not once per row. Keep exactly one prose exception: the push, where a mark cannot travel — and there the caveat belongs in the title suffix, not the body tail, so truncation cannot eat it. Data consequence to ship with it: add a confidence field to the compare token, or exclude unverified layers from the card. Accessibility: hollow/filled must be paired with a shape difference or a label, never color alone.

## Missing screens

- **The year at this address (12-month dated timeline)** (web/ios/android): F5, F6 and F12 all create annual dates — lease end, notice deadline, insurance renewal, HOA dues, county appeal window, state registration deadline — while composeForHome expands 14 days, so the loop's annual-return step has no surface at all. A 12-month timeline with one lane per source (You / city / county / state), today as a vertical rule and the 14-day window shaded, is the only place a user can see that their year is busy in March, and the only place seeded county and state rows read as context rather than as unexplained rows in a card titled 'at this address'. It is also the honest destination for the keeper's fact count and for the reminder lead indicator.
- **Today widget — large size (iOS systemLarge / Android 4x4)** (ios/android): The proposal specifies only small and medium, both of which are text stacks; nothing earns a larger cell. Large is where the year strip plus today's three lines fit together, making the annual promise visible with no notification and no app open — which is exactly the return trigger F7 exists to provide for users who declined push. It also gives the widget gallery a reason to sell more than one size, and it needs its own drawing: a 12-month strip and a 14-day strip in one frame is a layout decision, not a scale-up of the medium.

# LENS: Information architecture: four-tab fit, merge pressure, and the T1/T3 fork

**Verdict:** The proposed set is roughly 70 surfaces for a four-tab IA in which only two tabs (Place, Today) do any real work, and it is between 20 and 25 surfaces larger than the product needs. Three structural problems generate most of the excess. (1) "Today" names two different screens with two different payloads on every platform, so almost every feature is specified twice — F4, F5, F7 and F11 each carry a duplicate entry whose only reason to exist is the payload split. (2) There is no coherent "my place's facts" hub, so the same list of user-entered facts is drawn four times — as f2-first-week-checklist, f6-just-moved-card-synced, f5-your-dates-card and f11-keeper-knows-sheet — each with its own storage, its own dismissal and its own drift path. (3) "Tell the app a date" is specified as seven separate sheets (f5-add-date-sheet, f2-pickup-day-quick-set, f4-6-pickup-editor-entry, f6-voter-step-sheet, f12-calendar-event-detail-sheet, f5-remove-date-confirm, f10-3-extraction-confirm-sheet) when it is one sheet with modes. The T1/T3 split is worse than two parallel UIs: it is nine forks, three of them at the storage layer, and the doc has no migration that carries a user's dates, pickup rule, checklist ticks or keeper from SavedPlace.id to Home.id when they claim — so the highest-investment user loses everything they typed at the exact moment they invest most. That is a blocker, not a polish item. Net of my recommendations the set shrinks by about 23 surfaces while gaining one genuinely missing route (the place file) and one genuinely missing web route (bill detail, needed for push landings).

# LENS: Adversarial end-to-end flow walk: every surface a real user lands on, including auth, OS permission, tier promotion, and failure paths

**Verdict:** Strong within features, blind between them. The set genuinely catches the big structural holes (F5's management list, F7's discovery surfaces, F3b's gating states, the two-Today split) and its per-entry state lists are better than the doc's. But it is organized feature-by-feature, so every remaining gap sits in a seam where one feature's output is another's input: account creation, OS permission grants, saved-place→home promotion, and correction durability. Walking the ten flows end to end, nine surfaces are missing and two of them break the pilot's headline metrics before any feature is at fault — the email-verification step silently destroys the saved place the whole bridge depends on (flow 1), and iOS burns its one-shot notification permission at app launch, before the user has a place or a reason (flow 2). Flow 10 (saved place then claim) has no surface anywhere in the set despite being the most likely path for a mover. Flow 6's "Preview an address" CTA has no destination at all on Android. The set is roughly 80% of the real screen count; the missing 20% is where users get stuck with no way forward.

## Missing screens

- **Email-verification handoff carrying the held address (verify-email-sent + verify-email landing)** (web): Flow 1. register/page.tsx:132 routes to /verify-email-sent, and the previewed address lives in a device-local localStorage draft (pendingPlace.ts, 24h TTL). Verifying on a second device loses the place and the bridge never happens. The interstitial must name the held address and the landing must complete the save from the server-side draft.
- **Preview-lost recovery on the post-signup arrival** (web/ios/android): Flow 1. When readPendingPlace returns null (expired, cleared, different device, storage blocked), the arrival screen has nothing to save and the user drops into a generic empty Place with no explanation and no way back to the address they typed. Needs an inline re-entry, not an empty state.
- **Notification permission primer + denied recovery** (ios/android): Flow 2. AppDelegate.swift:50-61 fires the iOS system prompt at app launch, spending the one-shot grant before the user has a place or a reason. Every push in F4/F5/F3 depends on it and iOS never re-asks. The primer belongs at the briefing opt-in; the recovery row belongs in settings and on both opt-in cards.
- **Signed-in add-a-place sheet (address search + save)** (android/ios): Flows 1 and 6. The Place launch funnel is the signed-out root; Android's only save path reads a pending draft from signup. So f1-today-empty's 'Preview an address' and the widget's 'Save an address to see today here' both dead-end for a signed-in Android user with no place. iOS has SavePlaceSheet but no entry point from these surfaces.
- **Claim-success receipt: what moved with you** (web/ios/android): Flow 10. Claiming a previously saved address silently changes Today's payload and chip, orphans saved_place-scoped dates, resets the keeper, restates the widget label, and leaves a duplicate saved-place row. It also flips those dates from 'Only you' to household-visible, which is a privacy change that needs consent. The existing VerifiedSuccess screen (/app/place?verified=1) is the untouched natural host.
- **Native entry point to the briefing content (Today tab hosts Screen 1, or a delivered-briefings row)** (ios/android): Flow 2. TodayDetailView mounts only from a push deliveryId, so a native user with notifications off — or who swiped the push away — can never reach f4-2's pickup card or f4-3's quiet-day receipt. Design rule 4's in-app equivalent fails on iOS and Android.
- **Web bill detail route (/app/homes/[id]/bills/[billId])** (web): Flow 8. f10-7's reminder landing, F3's bill_paid notification, f10-5's provenance block and the f10-4 photo entry point all need a bill-shaped destination; web has only a list page, so every one of them lands on a list instead of the bill.
- **Owner-side 'confirm this person lives here' approval** (web/ios/android): Flow 4. f3b's upgrade path assumes a co-resident can complete address verification on a home someone else already claimed. If postcard, document and landlord flows do not accept a non-owner occupant there, every locked control leads to an uncompletable sheet — an owner-attestation path is the only way out.
- **Single 'this isn't right' report sheet** (web/ios/android): Flows 2 and 3. Two affordances are proposed for the same act ('Not my schedule' on the pickup card, 'This isn't right' on the event sheet) with no endpoint and no confirmation behind either, yet §5's honesty counter reads exactly this report as one of its two inputs.
