# Home task creation recovery — September 10, 2026

Ordinary task creation now has an opt-in exact retry contract. A native client can keep the same request identity through an interrupted response and recover the already saved task before starting private attachments. It cannot accidentally recreate a deleted or hidden original by repeating that request.

## Contract and boundaries

`POST /api/homes/:homeId/tasks` accepts the existing flat task fields plus a lowercase UUID `request_id`. Supplying this field requires the opening `x-pantopus-session-scope` from the authenticated task collection. The response is 201 for a first creation or 200 for recovery and contains the current task projection, `replayed`, the authenticated `task_session`, and `creation_receipt` with exact Home, actor, request, task, canonical payload hash and creation time. The service verifies these bindings before reporting success. Legacy requests without the field and Mail-source conversion retain their existing contracts.

The service-only `HomeTaskCreateReceipt` and RPC serialize against the current Home/authority locks. The receipt stores a canonical JSON payload hash, with the existing type aliases and title trimming; omission and explicit null remain distinct. Task, audit and receipt are atomic, including a final current-access check. The task UUID remains in the receipt after task deletion. Current denial blocks recovery; a changed payload is `HOME_TASK_CREATE_CONFLICT`, and a deleted or hidden original is `HOME_TASK_CREATE_RETIRED`. Neither result creates another task. Direct client receipt reads, writes, deletion and RPC execution are closed; no role defaults or hosted data change. The new Home dependency is explicitly included in both private setup and deletion policies: only this creator's private-setup receipts are eligible for the private exception. Foreign or established-household receipt history denies private access/deletion. An authorized Home deletion cascades its storage-free receipt records.

A recovered task contains its current fields and capabilities. The client must bind the receipt identity and any previously retained hash, rather than require the current task title to equal an earlier submitted title. A later legitimate edit must remain visible and must not be overwritten by recovery. An interrupted client operation must retain its exact UUID and input, including after 408/429, until recovery or a terminal result; attachments start only after the exact saved task is established.
