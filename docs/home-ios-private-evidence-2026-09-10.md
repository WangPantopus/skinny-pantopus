# iOS private claim evidence — 2026-09-10

## Scope and user behavior

This candidate connects the iOS claim wizard and claim-review surfaces to the committed private evidence lifecycle. It builds on the [private evidence backend milestone](home-claim-private-evidence-2026-09-10.md). It does not apply migrations or change hosted data, role defaults, ownership approval policy, or provider configuration.

The wizard uploads one supported manual property or residency document through an immutable private reservation. It sends the opening server session on upload and claim creation, preserves the same claim/upload identity and selected bytes across an unknown upload result, and finds an existing pending claim before creating another. Once an upload is attempted, file removal, replacement and document-type changes are locked while the same upload remains retryable. A visible My claims recovery action opens the existing private record for explicit cleanup instead of claiming that discarding local bytes deleted a saved file. A saved file remains pending evidence. The screen no longer derives an address verdict from the filename or suggests that uploading an ID, title, or escrow file supplies verified evidence. Review and approval remain separate decisions.

The Home reviewer and platform reviewer can list exact private records, open authenticated bytes, inspect the supported document rendering, and explicitly verify one evidence item. The client retains the exact review token and inspection receipt when a verification result is unknown. It hides the bytes during recovery and retries the same decision; an authorization denial retires the receipt. HTTP 408 and 429 remain retryable, including when they follow an earlier unknown outcome. The same classification applies to the existing Home and platform claim decisions. It never automatically approves the claim.

The My claims destinations in both Hub and You now resolve the exact claim from the signed-in account's authenticated list and open its documents. An active ordinary claim can add evidence. A withdrawn claim can reopen its remaining pending documents and retire them under the existing protected withdrawal authorization; it cannot add files. Storage-cleanup failures remain visible and the exact retired record can be retried without erasing its history.

## Request and display boundaries

- Every private client captures the opening API environment, account, local session, and first server session. Current identity is checked before requests and after responses. An old screen or late picker/response cannot bind a replacement session.
- Reviewer panels bind the displayed platform review token or a newly fetched exact Home claim detail token before the first list. A changed snapshot cannot be silently adopted; the bound token advances only after the panel's own successful verification.
- Downloads require the identical current ready/available evidence record before and after the bytes return, including record identity, metadata and state. A pending reviewer inspection also requires the unchanged current review token and authority. Concurrent retirement, removal, metadata change or review change discards the bytes.
- A failed access recheck clears displayed filenames and document bytes. Leaving the evidence screen retires its client and pending local data. Unknown verification retains only the exact decision receipt, without a preview.
- PDFs render as native page images; supported images use ImageIO thumbnail decoding capped at 1,600 pixels on their longest dimension and render with UIKit and plain text as escaped SwiftUI text. Bytes stay in memory without a public URL, external viewer or export action. An unrenderable document cannot enable verification.
- Uploads use the same 25 MB and manual evidence-type limits as the private backend. Evidence multipart filenames include an explicit UTF-8 `filename*` parameter; a non-ASCII filename is preserved by the deployed Busboy parser instead of becoming a conflicting reservation on retry.
- APIClient exposes authenticated response headers for inspection receipts while retaining the existing request/refresh/retry pipeline. Generic multipart callers keep their existing behavior.

## Remaining acceptance and limits

This is the native source checkpoint for private evidence, not complete Home acceptance. An installed-app visual journey through Files selection, PDF/image/text inspection and the review controls still needs explicit acceptance evidence. No real claimant document or hosted provider operation was used for these local checks. The generic household-request path retains its existing backend contract and is not claimed to have the new evidence session precondition. Dedicated ownership challenge/transfer/lease workflows and the remaining relationship/residency decision receipts remain separate backlog items. Native task attachments follow this checkpoint. Paid subscriptions and launch dependencies remain deferred together to the final launch-preparation step.
