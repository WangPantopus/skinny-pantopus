## Real app verification

The apps used a real local Node backend and local Supabase/PostgreSQL database,
with synthetic accounts and data. Hosted services were not used. A local
forwarding proxy preserved the signed mobile request host and session cookies;
it delayed real backend replies or injected failures for the specified cases.
Failure injection is distinguished from physically disabling Android networking.

Android ran on a dedicated API 35 emulator. iOS ran on a dedicated iPhone 17
simulator with iOS 26.5. The web app ran in a browser from the same review
checkout. Launch-cut flags stayed unchanged.

### Android Support Train privacy

These checks used the APK artifact from the exact #2152 CI run listed above.

- Signed in through the native UI and opened a synthetic private Train. The
  online screen showed its private story.
- Left the app, disabled emulator Wi-Fi and mobile data, and resumed it. The
  title and safe summary remained; the private story was absent. Reconnecting
  restored freshly checked detail.
- Entered an unsent organizer update. Leaving and returning offline hid the
  draft form and organizer details. A successful recheck restored the draft.
  The visible Send update label was disabled while private detail was withheld.
- Delayed a real detail reply, left the visit, and resumed offline. The late
  reply did not restore the private story.
- Injected a 403 on a refreshed detail read. Both the retained title and private
  story disappeared; the screen offered retry. Removing the failure allowed
  recovery.

No organizer update was broadcast. Reservation creation, delivery confirmation,
fund payments, physical-device snapshots and every account-switch race are not
certified by these checks.

### Android post lists from 2166

The local fixture contained 240 posts and bookmarks. My posts retained rows
230–234, and Saved posts retained rows 234–238, with exactly the same visible
row bounds before and after opening a post and returning. Each return made one
list read whose real response was delayed. Rows stayed visible while the read
was pending and after completion. Both lists also retained those rows and their
reading position after leaving the app and returning with emulator Wi-Fi and
mobile data disabled.

The following mutation case failed on the same APK:

1. In Saved posts, load beyond 200 entries and open synthetic post 235.
2. Use Post options → Remove bookmark. The write returns 200. Reopening the
   options shows Save post, confirming the detail now considers it unsaved.
3. Return to Saved posts. A fresh Saved-post list read succeeds, but post 235 is
   still displayed, including its Remove action.
4. The local database contains no bookmark for that post and account.

The cause is
[`SavedPostsViewModel.kt:125–139`](https://github.com/WangPantopus/skinny-pantopus/blob/4f9dfc6cd00f7b7a395c685090caa185a7bda489/frontend/apps/android/app/src/main/java/app/pantopus/android/ui/screens/my_posts/SavedPostsViewModel.kt#L125).
Refresh is capped at 200 entries. `replaceRefreshedHead` appends old rows below
that response's time boundary without checking whether they were unsaved or
became unavailable. Subsequent paging appends and deduplicates; it does not
remove an old row omitted by the server. The already-merged invalidation work
does trigger the read, but it cannot reconcile this ViewModel's retained tail.

Treat this as a P2 functional defect and a merge blocker for #2166. Reconcile
confirmed removals by post ID and/or revalidate retained pages before treating
them as current. Preserve the reading-position behavior that passed above.
Repeat this native case after the fix, including removal from another surface.
The synthetic bookmark was restored after the reproduction. No separate open
focused PR inspected here supplied this tail-reconciliation fix.
