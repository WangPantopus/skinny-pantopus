# Home invitations and exact-resource sharing

Source checkpoint in `/private/tmp/pantopus-home-permission-boundaries`, branch
`codex/home-permission-boundaries`, draft PR #32. This is a bounded authorization
milestone, not a hosted migration, ordinary-role rollout or full Home release.

## Invitations and household requests

Creation, preview, acceptance, decline/revocation, received/issued invitation
lists, and household-request creation/review/listing now use service-only SQL
transactions. The transactions lock the Home, current membership/ownership and
overrides, role/preset policy, source requests and invitations before deciding.
Direct client access to the invitation and household-request authority tables is
closed, including inherited PUBLIC privileges.

Invitation acceptance binds to an exact targeted user ID first. Email-only
invitations require the canonical confirmed Auth email; mutable public profile
email cannot substitute. Email-bound redemption locks the exact Auth identity
against concurrent email changes. An explicit open link requires the raw token;
an invitation ID alone cannot redeem it. One recipient wins, and an exact retry
returns only that recipient's current eligible membership without reapplying a
role, reopening expired/revoked membership, or replaying notifications. A viewer
declining an open link cannot revoke it for everyone else.

Tokens are generated by the backend; HomeInvite stores only their hashes. The
raw token is returned on creation and used by the invitation delivery channels.
Received/issued lists and public previews omit hashes, raw
tokens, policy snapshots and street addresses. Legacy hash-null token lookup is
retained with the same current authority and recipient checks.

Current inviter authority includes explicit deny, verification/status, known
role, age and both membership/access date windows. Proposed and existing target
rank, the complete future permission set and every explicit preset grant must
fit the inviter's current authority. Child/teen ceilings remain hard limits;
historical unknown ages remain compatible. Existing restrictive overrides are
preserved. A new child preset records the child ceiling. Pending access windows
are intersected, future access stays future, and an already-verified membership
is not rewritten. A saved policy snapshot prevents later default/preset changes
from enlarging an already-sent invitation.

Household intent alone grants no access. Approval locks the exact stored request
recipient and atomically creates the invitation plus source decision/audit.
Ownership requests return the dedicated ownership-flow response. Acceptance
rechecks that request's current approved recipient, resolver and requested role.
Audit failure rolls back both invitation state and admission. Auth-state/transport
failures surface as retryable 503 responses rather than direct-table fallbacks.

The web callback chain now returns the created token to the UI. Both invitation
forms show the usable link; the QR flow encodes that exact link using the shared
real QR component. Local date selections become explicit UTC instants; the end
day is inclusive and uses calendar arithmetic across daylight-saving changes.
Email creation remains committed if delivery fails, and the UI reports failed
or preview-only delivery truthfully.

Notification delivery remains best effort. An unknown/lost creation response can
leave a committed pending invitation without a recoverable link in its list DTO.
Revoke/reissue controls and ambiguous-send recovery still need explicit web/native
UI acceptance; this checkpoint does not claim guaranteed delivery or automatic
create-response recovery.

## Guest and scoped sharing

Guest-pass and scoped-grant issuance, listing, revocation and consumption use
service-only transactions. Issuers need current management authority and the
exact resource read permission. Issuance snapshots the exact Wi-Fi/emergency/
document IDs; later-added resources do not join an existing link. Consumption
rechecks current issuer, named recipient, time window, revocation, passcode,
quota, exact record and visibility. Existing recipient age/status/unknown-role
and explicit denies remain effective. A no-credential visitor may use an
intentionally public bearer link; supplied invalid credentials cannot downgrade
to anonymous access.

Only public/member-visible records are eligible for this bounded external
sharing contract. Private creator setup is not an external-sharing grant.
Unimplemented edit/upload grants are rejected instead of advertised. Legacy
unvalidated links require reissue. An exact issuer may revoke an old link even
after losing management permission. Legacy direct scoped-RLS access is closed
because it exposed entire unreviewed rows; named recipients use the same narrow
DTO/receipt API. Ordinary member permission branches are unchanged.

Public responses project exact fields and omit arbitrary details, private
storage paths and hashes. A document view issues a short-lived hashed receipt
bound to exact documents, recipient and share. Download rechecks before and
after storage fetch, then atomically consumes that document from the receipt.
One original view spends quota once; a max-views=1 document remains downloadable
once without charging a second view. Concurrent final consumption has one
winner. Storage errors, changed records or changed access cannot return bytes.
Downloads use an attachment response and private/no-store headers.

Guest/scoped forms now produce the actual `/guest/:token` and `/shared/:token`
routes. The shared QR encoder's rendered SVG is independently decoded in tests
for guest, scoped and invitation URLs.
